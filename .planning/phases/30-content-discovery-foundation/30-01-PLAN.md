<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Checked-in registries -> public discovery helpers | Maintainer-authored project, writing, theme, and topic records become public topic/reference data. |
| Public route/filter/feed/preview consumers -> `maybe...` lookups | Later visitor-facing surfaces will call nullable helpers with arbitrary slugs or labels. |
| Validation findings -> terminal output | Maintainer-only diagnostics expose reasons that must not become public helper results. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-01 | Information Disclosure | `maybePublicTopicBySlug()` and `publicContentReferences()` | mitigate | Compose only `publicProjectIndexProjects()`, `publicWritingEntries()`, and `publicThemeEntries()`; return `null` for unknown/non-public inputs without reason fields. |
| T-30-02 | Information Disclosure | Topic slug and label lookup | mitigate | Keep hidden/draft/archived/unsupported diagnostic reasons only in `topic-validation.ts`; public helpers return `TopicRecord`, `PublicTopic`, arrays, or `null`. |
| T-30-03 | Tampering | Canonical label/alias map | mitigate | `validateTopicRegistry()` detects duplicate slugs, invalid slugs, duplicate display orders, and colliding normalized labels/aliases before downstream routes consume topics. |
| T-30-04 | Information Disclosure | Downstream consumer imports | mitigate | Export a safe `PublicContentReference` envelope so feeds, filters, related work, and previews do not need full registry records or duplicated visibility guards. |
| T-30-05 | Repudiation | Curation diagnostics | mitigate | Structured issue codes and `topic/{slug}` CLI prefixes identify the exact maintainer-facing source without exposing those details in public runtime helpers. |
| T-30-06 | Denial of Service | Curation verification | accept | The corpus is small checked-in data, no visitor runtime path is added, and validation runs locally in `bun run verify:curation`. |
</threat_model>
