# Phase 19 - UI Design Contract

> Visual and interaction contract for Theme Domain Foundation. Generated by gsd-ui-researcher, pending verification by gsd-ui-checker.

---

## Scope Locks

Phase 19 is a domain/data foundation phase. It must create the trusted theme data, helper, and validation surface that future theme routes consume, but it must not implement visible `/themes` UI.

In scope:

- Add typed checked-in theme domain data, pure selectors, route path helpers, relationship helpers, and theme-local validation.
- Keep theme records as curated paths through existing project and writing registries, not as a second source of project or writing display copy.
- Validate public theme eligibility, stable ordering, required fields, slug quality, status support, selected project relationships, and public writing relationships.
- Wire theme validation into the existing curation verification surface so maintainers see actionable developer-facing failures.

Out of scope:

- No `/themes` index route, `/themes/{slug}` route, primary navigation item, footer addition, visible theme card rendering, page layout, collaboration panel, metadata, sitemap behavior, browser release check, or release-readiness copy.
- No route-visible OpenLinks promotion, theme CTA, search/filter UI, CMS/admin UI, Markdown/MDX parser, runtime content fetch, dynamic Open Graph route, analytics, comments, newsletter, or live link reachability.
- No new UI dependency, shadcn initialization, third-party UI registry block, icon library, or visible animation.

Future phases:

- Phase 20 owns theme route UI in the dark-primary interface.
- Phase 21 owns collaboration panels and cross-links.
- Phase 22 owns theme metadata, structured data, sitemap, and social preview behavior.
- Phase 23 owns theme browser/static/release verification expansion.

Design system notes:

- Mystic UI is already pinned in `package.json` to `github:pRizz/mystic-ui#d36017757708ed01ef2b3b47beb14f294726411c`.
- Phase 19 domain modules must not import `solid-js`, `mystic-ui`, components, route files, DOM globals, or visual-motion helpers.
- Future Phase 20+ theme route UI must stay dark-primary by default. Do not introduce light-first utilities such as `bg-white`, `bg-stone-50`, or `text-zinc-950`.
- Do not use nested cards. Cards are allowed only for repeated theme items, related project/writing items, collaboration panels, modals, and genuine fallback states in later phases.
- Keep card and panel radius at 8px. Chips may keep the existing 6px radius.
- Future routes should reuse existing classes before adding new theme-specific classes. New classes must preserve the same dark shell, wrapping, focus, and motion rules.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Inline label gaps, compact metadata gaps |
| sm | 8px | Chip rows, compact link rows, small card gaps |
| md | 16px | Default grid gaps, paragraph-to-meta spacing, relationship list gaps |
| lg | 24px | Card padding, panel padding, proof-point grouping |
| xl | 32px | Theme section gaps and future detail layout gaps |
| 2xl | 48px | Page top/bottom rhythm through existing shell spacing |
| 3xl | 64px | Major page separation and sticky-header offset only |

Exceptions:

- Phase 19 must not add route-visible spacing tokens because it does not render `/themes`.
- Preserve existing shell horizontal padding of 20px (`px-5`) from `.site-main`, `.site-header-inner`, and `.site-footer-inner`.
- Future clickable links and buttons must keep at least a 44px touch target through existing `min-h-11` and `min-w-11` patterns.
- Existing anchored-card sticky-header offset of 64px remains valid for future theme cross-links.
- Existing chip radius of 6px and card/panel radius of 8px are accepted local exceptions to the 8-point spacing rhythm because they are already part of the visual system.

## Typography

Use exactly these four sizes and two weights for any Phase 20+ route-visible theme content. Phase 19 data and tests must not introduce visible typography.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 600 | 1.4 |
| Heading | 20px | 600 | 1.25 |
| Display | 36px | 600 | 1.15 |

Typography rules:

- Future theme index and detail routes must use `.page-title` for H1 display text, `.lead` for summary copy, `.section-title` or `.card-title` for nested headings, and `.body-copy` or `.card-copy` for paragraphs.
- Theme detail pages must expose a single H1 and ordered headings that describe the content graph: theme idea, proof points, related projects, related writing, and collaboration angle.
- Do not add new font families, negative letter spacing, viewport-scaled font sizes, or weights beyond 400 and 600.
- Theme titles, project names, writing titles, tags, URLs, and generated relationship labels must use `min-width: 0` plus `overflow-wrap: anywhere` or equivalent existing classes.
- Helper-derived copy must be concise enough for cards and metadata surfaces. Theme summaries should remain one short paragraph; proof points should remain scannable list items.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#050608` | Root background, body background, dark page depth |
| Secondary (30%) | `#18181b` over `#0d1117` | Future theme cards, nav, panels, repeated relationship items, detail asides |
| Accent (10%) | `#6ee7b7` | Future theme links, labels, chips/pills, hover borders, selected proof-point emphasis, primary CTA fill, selection background |
| Focus | `#67e8f9` | Focus-visible rings only |
| Warning/callout | `#fcd34d` amber border | Non-destructive notices only |
| Destructive | none | No destructive actions exist in Phase 19 |

Accent reserved for:

- Future theme index/detail action links such as `Explore theme`, `Project details`, and `Read note` or `Read essay`.
- Theme status/category labels, audience labels, proof-point labels, relationship chips, and hover borders.
- Subtle reactive card glow and text selection background.
- Not for broad page backgrounds, decorative orbs, primary OpenLinks promotion, or every interactive element.

Color rules:

- Route-visible content must remain dark-primary. Default text must stay `#f4f4f5`, `#e5e7eb`, `text-zinc-50`, or `text-zinc-300`; supporting text may use `text-zinc-400`.
- Focus remains cyan and visible. Do not rely on color-only hover states.
- Curation validation failures are developer/test output, not route-visible red/destructive UI.
- Future empty and unknown theme states are neutral dark surfaces, not destructive surfaces.

## Phase 19 Data And Validation Contract

### Theme Domain Data

- Theme records may contain `slug`, `title`, `summary`, `status`, `displayOrder`, `audience`, `proofPoints`, `collaborationAngle`, `relatedProjectSlugs`, and `relatedWritingSlugs`.
- Theme records must not duplicate existing project one-line copy, project story copy, writing summaries, writing body copy, or authored external-link labels.
- Relationship arrays preserve authorial ordering so future UI can render the most relevant project and writing examples first.
- Hidden, draft, unsupported, archived-only, or otherwise non-public theme records must stay out of public selectors and future route derivation.

### Helper-Derived Relationships

- Future route UI must derive related projects through theme helpers that resolve selected public project detail records.
- Future route UI must derive related writing through theme helpers that resolve public writing entries.
- Display components must consume resolved records, not raw slugs, whenever they render titles, summaries, links, or metadata.
- Helper functions should defensively return only resolved public records even though validation is expected to fail invalid relationships.

### Validation Output

- Validation failures must identify the theme record and issue precisely enough for maintainers to fix the source data.
- Error output should use a `theme/` or `themes/` prefix and stable issue codes.
- Validation copy is developer-facing. It should describe the bad field and remediation path without route-visible marketing language.
- The curation gate should fail on duplicate/malformed slugs, duplicate display orders, unsupported public status, missing required fields, empty proof points, empty relationship arrays, unknown project slugs, hidden or unselected project references, unknown writing slugs, and unpublished writing references.

## Future Route Consumer Contract

When Phase 20+ consumes Phase 19 theme helpers, it must preserve these visual and interaction constraints:

- The first viewport for `/themes` must be the actual theme browsing surface, not a marketing landing page or oversized hero.
- Theme index cards must be repeated item cards, not nested cards inside a larger section card.
- Theme detail pages must start with a compact `.page-intro`, a single H1, readable lead text, and visible proof/context before any large decorative element.
- Related projects and writing must render from helper-resolved records and use existing project/writing action labels where applicable.
- Related theme links on project or writing surfaces must be low-density contextual links that clarify the graph without overwhelming the primary project or writing narrative.
- Only links and form controls may be interactive. Do not make entire cards clickable through JavaScript handlers.
- Existing `ReactiveSurface` behavior may wrap future theme card grids, but no new JavaScript animation is allowed unless a later phase explicitly justifies it.
- Reduced-motion, coarse-pointer, and mobile guards in `src/styles/app.css` must remain effective.
- Future route UI must pass desktop and mobile dark rendering checks, contrast/readability checks, keyboard focus checks, and text-overlap checks.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Phase 19: none. Future theme route default: `Explore theme` |
| Empty state heading | Phase 19: none. Future route default: `No public themes yet` |
| Empty state body | `Theme paths will appear after public theme records pass curation.` |
| Error state | Developer-facing: `Theme curation failed. Fix the listed theme records and rerun bun run verify:curation.` |
| Destructive confirmation | none; Phase 19 has no destructive actions |

Copy rules:

- Phase 19 must not add user-facing `/themes` copy.
- Theme copy must be accurate, authored, and theme-specific. Do not use placeholder/template content.
- Future visible theme route copy should name the theme, audience, proof points, collaboration angle, and helper-derived project/writing relationships without repeating full project or writing prose.
- Do not mention CMS, MDX, drafts, hidden records, unsupported records, analytics, comments, newsletter, runtime fetches, or dynamic image generation in route-visible copy.
- Link labels must identify the destination or action; do not use `click here`, `learn more`, or repeated ambiguous `read more` labels.

## OpenLinks Identity Contract

- Phase 19 must not add any new visible OpenLinks placement.
- Preserve OpenLinks as a subtle identity signal through existing profile/footer/contact/metadata surfaces.
- Existing footer copy remains the visible low-intrusion placement: `OpenLinks profile` with `rel="me noopener noreferrer"`.
- Future theme collaboration panels may reference OpenLinks only as an identity hub or profile link when helper/profile data already provides it.
- OpenLinks must not become the primary theme CTA. Bright Builds, selected projects, writing entries, reviewed source links, and practical collaboration context stay primary.
- If future metadata reuses `personJsonLd()` or `profileSameAsLinks()`, OpenLinks may remain in `Person.sameAs`; do not add metadata-only promotion that contradicts visible placement.

## Verification Contract

Phase 19 verification should prove the domain foundation without claiming visible route coverage.

Implementation must prove:

- Theme helpers expose public theme entries, stable `/themes/{slug}` paths, and ordered detail route arrays without route files.
- Hidden, draft, unsupported, archived-only, or otherwise non-public theme records stay out of public selectors and route derivation.
- Relationship helpers resolve only selected public project detail records and public writing entries.
- Validation fails for invalid theme data and relationship errors with precise stable issue codes.
- `scripts/verify-curation.ts` aggregates theme validation beside project and writing validation.
- Domain modules stay visual-framework-free: no Solid, Mystic, component, route UI, DOM, or animation imports.
- `bun run verify:visual-system` continues to pass, proving the new domain surface did not cross visual boundaries.

Recommended commands for executor verification:

- `bun run format:check`
- `bun run check`
- `bun run typecheck`
- `bun run test`
- `bun run verify:curation`
- `bun run verify:visual-system`

Do not add Phase 20 browser checks, static `/themes` output checks, metadata checks, sitemap checks, or release evidence labels in this phase.
