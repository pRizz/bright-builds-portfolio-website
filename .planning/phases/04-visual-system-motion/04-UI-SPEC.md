## Spacing Scale

Declared values use multiples of 4. New Phase 4 styles should use this scale instead of ad hoc spacing.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Inline icon/text gaps, focus outline offsets, subtle divider spacing. |
| sm | 8px | Chip gaps, compact row gaps, small vertical rhythm inside dense labels. |
| md | 16px | Default paragraph/card internal rhythm, list gaps, grouped inline link gaps. |
| lg | 24px | Card padding, route section padding, hero column gaps on mobile, panel padding. |
| xl | 32px | Desktop grid gaps, major component separation, hero inner rhythm. |
| 2xl | 48px | Section-to-section spacing on mobile and compact desktop. |
| 3xl | 64px | Page-level section breaks and desktop route rhythm. |

Exceptions:

- Interactive targets must be at least 44px tall/wide even when their visual padding is smaller.
- Existing `max-w-6xl` page width remains the shell constraint: 72rem maximum content width.
- Cards, panels, notices, buttons, and focusable link blocks use 8px radius maximum. Do not introduce pill cards or nested rounded-card containers.
- Existing Phase 3 `20px` Tailwind `p-5`/`px-5` spacing may be preserved only where untouched; newly polished card/panel surfaces should normalize to 24px.
- Border widths are 1px by default; current-focus rails may use 4px.

## Typography

Use exactly these four type sizes and two weights. Do not add negative letter spacing or viewport-fluid font sizing.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | Regular 400 | 1.5 |
| Label | 14px | Semibold 600 | 1.4 |
| Heading | 20px | Semibold 600 | 1.25 |
| Display | 36px | Semibold 600 | 1.15 |

Typography rules:

- Body copy, route leads, project explanations, and contact copy use Body.
- Eyebrows, metadata, chip labels, tier/status pills, counts, and small support copy use Label.
- Card titles, section titles, panel titles, and theme titles use Heading.
- Route H1s use Display. If the 320px browser check proves a specific H1 overflows, wrap the text naturally before reducing size.
- Use `text-wrap: balance` only for display or section headings where it improves wrapping without hiding content.

## Color

The site is dark-primary. Default rendering must keep `.dark` active on the root document and `color-scheme: dark`.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#050608` with `#0d1117` depth | Page background, app shell, route body, dark browser theme. |
| Secondary (30%) | `#18181b` / `rgba(24,24,27,0.75)` | Cards, panels, header/footer bands, project rows, grouped surfaces. |
| Accent (10%) | `#6ee7b7` emerald, `#67e8f9` cyan, `#fcd34d` amber | Reserved elements listed below only. |
| Destructive | `#f87171` | Destructive actions only. No destructive actions are in scope for Phase 4. |

Accent reserved for:

- Primary CTA background and selected link emphasis.
- Focus-visible rings and keyboard outlines, using cyan.
- Hover/focus borders for interactive cards and project rows, using emerald.
- `::selection`, tier/status pills, and compact labels where emphasis improves scanning.
- The current-focus / "Now building" rail or marker, using amber.
- Pointer-reactive highlight fields when enabled, using low-opacity emerald/cyan only.

Color prohibitions:

- No decorative gradient orbs, bokeh blobs, or generic purple/purple-blue gradient backgrounds.
- No one-note slate/dark-blue UI. Dark neutral surfaces must be balanced with restrained emerald/cyan/amber accents and warm lower-depth tones already present in the shell.
- Avoid light-first utility classes such as `bg-white`, `bg-stone-50`, and `text-zinc-950` unless the local reason is documented next to the change.
- Text contrast must remain readable on desktop, 390px mobile, and 320px mobile dark rendering.

## Phase 4 Visual Contract

### Layout

- Preserve the Phase 3 information architecture: home identity plus current focus, project stories, grouped project index, about themes, contact cards, footer identity link, and existing static metadata.
- The first home viewport must show Peter Ryszkiewicz / pRizz, Bright Builds context, the `Browse projects` CTA, and the `Now building` surface with a hint of the next section on common desktop and mobile viewports.
- Use full-width shell/header/footer bands and unframed route sections. Cards are for individual repeated items, notices, and project/contact/theme surfaces only.
- Do not place cards inside other cards. Do not wrap page sections in decorative floating cards.
- Header navigation must wrap cleanly at 320px without horizontal scroll or overlapping the brand.
- Project cards and contact cards must expose all critical links through normal anchors. Hover affordances must also be visible through focus and tap states.
- Chips, status pills, labels, and project titles must wrap without resizing the card grid or causing horizontal overflow.
- Project anchors must keep stable IDs and readable scroll position. Preserve `scroll-margin-top` for sticky-header deep links.

### Visual Assets

- Use local or checked-in assets only. Allowed source assets are `public/social/bright-builds-og.png`, `public/favicon.svg`, `public/icon-192.png`, and `public/apple-touch-icon.png`.
- A new decorative or brand asset may be added only under `public/`, with optimized dimensions and no remote runtime dependency.
- Decorative assets must be marked `aria-hidden="true"` or applied through CSS backgrounds. Informational assets need alt text that names the represented work.
- Visual assets must not obscure text, reduce contrast, push content below the fold unnecessarily, or become the primary portfolio subject.
- Do not paste the social card as a literal card screenshot. If it is used visually, adapt it as texture, crop, or brand material that supports the live content.

### Components

- Keep shared visual primitives in `src/styles/app.css` under Tailwind component layers unless a Solid component genuinely removes duplication.
- Route components should stay thin and consume `src/domain/*` selectors. Do not move motion state, pointer math, or Mystic internals into domain modules.
- If a visual-system helper needs pure configuration, place it in a UI-focused module and unit test the pure decision logic.
- Local component names should describe the surface, for example `ReactiveCard`, `ProjectHighlight`, or `VisualShell`, not library internals.

## Motion Contract

Motion is supportive, not the centerpiece.

| Motion Type | Contract |
|-------------|----------|
| Hover/focus transitions | 120ms, transform/color/border/background only, `ease-out` or existing CSS `ease`. |
| Card lift | Max `translateY(-2px)` plus border/shadow response. No scale above `1.01`. |
| Pointer-reactive highlight | Optional. Use one `requestAnimationFrame` loop per mounted surface group, transform/opacity/background only, and no layout reads inside the animation frame after setup. |
| Ambient detail | Optional and route-stable. No infinite autoplay animation unless it stops under reduced motion, hidden tabs, coarse pointer, and unmount. |
| Route/page motion | No scroll-jacking, no delayed content reveal, no animation required to read content, no layout-affecting animation. |

Reduced-motion and device gates:

- Under `prefers-reduced-motion: reduce`, disable non-essential transforms, opacity fades, pointer-reactive effects, smooth scrolling, animation loops, and transition duration beyond the existing `0.01ms` guard.
- Preserve the current high-specificity `:root *` reduced-motion cascade unless the executor replaces it with a more reliable local adapter and proves parity in browser verification.
- On coarse pointer devices and at 390px/320px viewports, disable pointer-following effects. Keep tap/focus color and border feedback.
- When `document.visibilityState !== "visible"`, pause or cancel `requestAnimationFrame`, timers, observers, and pointer work.
- Effects must clean up listeners, observers, timers, and animation frames on unmount. Cleanup belongs in Solid lifecycle code, not domain helpers.

Performance limits:

- Animate `transform`, `opacity`, `background`, `border-color`, and `box-shadow` only.
- Do not animate width, height, top, left, margin, padding, grid tracks, or text size.
- No Matter.js, Rapier, Three.js, WebGPU, GSAP, or heavy physics libraries in Phase 4.
- Do not add `motion` or `@solid-primitives/spring` unless planning proves CSS/local Solid utilities cannot satisfy a specific interaction.

## Accessibility Contract

- Every interactive surface must be keyboard reachable through native anchors/buttons or explicit focus handling.
- Focus-visible rings use cyan and must remain visible against dark surfaces.
- Touch targets are at least 44px tall/wide.
- Important content must never be hover-only. Hover-only decoration is allowed only when the same card/link remains fully understandable without it.
- Keep semantic headings, lists, articles, nav, main, and footer intact. Visual wrappers must not hide route headings, project anchors, contact links, or JSON-LD/source metadata.
- Do not introduce in-page explanatory copy for animation behavior. The accessibility outcome should come from defaults, not instructions.
- OpenLinks remains one low-intrusion visible identity placement in footer/about/contact contexts plus metadata where already supported.

## Non-Goals

- No per-project routes, per-project OG images, blog/writing system, CMS, search/filtering, analytics, backend services, or release-wide Lighthouse budget work.
- No heavy 3D, WebGPU, full physics simulation, constellation graph, scroll-jacking, autoplay animation centerpiece, or decorative gradient-orb motif.
- No rewrite of Phase 3 narrative/content hierarchy for style alone.
